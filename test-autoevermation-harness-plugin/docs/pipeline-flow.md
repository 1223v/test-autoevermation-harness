# 요청별 실행 흐름

정본: [full-pipeline](../skills/full-pipeline/SKILL.md), [공용 정책](../references/execution-policy.md).
양쪽 호스트에서 메인이 역할을 직접 수행한다. Claude는 JDT LS와 승인·순서 훅, Codex는 JavaParser·소스 근거를 사용한다.

```mermaid
flowchart TD
 A[사용자 요청] --> B{요청 종류}
 B -->|조회| R[기존 결과와 신선도 보고]
 B -->|테스트 실행| T[대상 1회 실행 후 결과]
 B -->|커버리지 측정| M[유효 결과 공유 또는 1회 실행 후 측정]
 B -->|생성 또는 개선| C[저장 설정·확인 가능한 정보 사용]
 C --> E{환경 준비 필요}
 E -->|예| S[변경 내용을 묶어 동의 → setup-harness → 원래 작업 재개]
 E -->|아니오| D[필요한 분석·시나리오 설계]
 S --> D
 D --> Q[권고와 시나리오를 함께 제시 → 승인 범위 확정]
 Q --> G[승인 시나리오 최초 생성]
 G --> V[6 실행 → 8 커버리지 → 9 적합성]
 V --> P{선택 목표와 승인 시나리오 충족}
 P -->|예| O[ok와 실행 증거]
 P -->|아니오| L{공용 예산·종료 조건}
 L -->|종료| X[partial과 잔여·중단 이유]
 L -->|예약 성공| F[실패 → 적합성 → 커버리지 순으로 한 묶음 수정]
 F --> V
```

빠름 총 1회·균형 총 3회는 모든 보정 원인을 합산한다. 마지막 수정 뒤 검증도 반드시 수행한다.
엄격/정책 없는 기존 설정은 동일 실패·gap 3회 무진전, 적합성 최대 3라운드·동일 unmet 즉시 종료를 유지한다.
자동 재개는 예산을 초기화하지 않는다. 전체 범위가 검증된 마지막 실행이면 별도 회귀 실행하지 않는다.
